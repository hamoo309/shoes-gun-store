# خطة تحضير الإنتاج والانتقال والتراجع

## حدود المهمة وحالتها

تاريخ الخطة: 2026-10-22. العمل الحالي تحضير وفحوص آمنة فقط. لا نشر، ولا Migration على قاعدة المتجر، ولا Seed/reset، ولا تغيير بيانات/حسابات، ولا نقل أو حذف صور. ملف `.env` الحالي وبيانات الدخول والأسرار لا تُستبدل. أوامر هذه الوثائق لعملية مستقبلية معتمدة وليست خطوات نُفّذت الآن.

Docker غير متاح على جهاز المراجعة؛ بناء الحاويات وتشغيل TLS واختبار volumes واستعادة Docker وهجرة نسخة مستعادة تبقى بوابات قبول على مضيف معزول. يذكر تقرير المهمة الاختبارات التي نُفذت فعلًا، بما فيها أي تجربة PostgreSQL معزولة. لا تعتبر قائمة قبول غير مملوءة دليل نجاح.

## جرد ما قبل الانتقال

قاعدة PostgreSQL تشمل الطلبات والمخزون والماليات وحسابات المسؤولين وhashes كلمات المرور والجلسات والتدقيق. لا يحتاج المتجر القائم حسابًا جديدًا بعد الاستعادة. الصور ملفات محلية عامة والإثباتات ملفات محلية خاصة؛ لا تتضمن هذه الخطة نقلًا لتخزين خارجي.

في قراءة ملفات 2026-10-22 كان `storage/products` يحوي 76 ملفًا و`storage/private` فارغًا، مع 9 صور مرفقة بمصدر web. هذه ملاحظة وليست أرقامًا تُفرض على اللقطة النهائية؛ قد تتغير بعمل المستخدم. لا تُنشئ إثباتًا تجريبيًا على المصدر لإتمام قائمة تحقق.

سجّل لكل نسخة/إصدار: مرجع المصدر وlockfile وإصدارات Node/PostgreSQL/Prisma، مراجع api/web السابقة والجديدة، SHA-256 لملفات migrations، أسماء قاعدة المصدر والهدف ومشروعي Compose وvolumes، وقت اللقطة والمنطقة الزمنية، بصمات الوسائط، ومسؤول القرار. لا تسجل سرًا أو token طلب أو بيانات عميل في تقرير المراجعة.

## مراجعة المخطط والهجرات

| Migration | أثرها ومراجعتها |
| --- | --- |
| `202610160001_initial` | إنشاء مخطط المتجر وجداوله وقيوده؛ لا تعِد تشغيلها كإعداد يدوي فوق نسخة موجودة. سجلها محفوظ في `_prisma_migrations`. |
| `202610160002_invariants` | CHECK constraints للأسعار والمخزون والإجماليات والمرتجعات؛ قد ترفض بيانات قديمة مخالفة إذا لم تكن مطبقة. لا تُصلح بيانات المتجر تلقائيًا. |
| `202610180001_color_images` | إضافة `ProductImage.color` القابل لـNULL وفهرس، دون استبدال عناوين الصور أو كتابة ملفات. |
| `202610220001_auth_login_attempts` | جدول `AuthLoginAttempt` وفهرسه لمخزن محاولات الدخول المشترك. Migration جديدة إضافية مُحضّرة في المصدر ولم تُطبّق على القاعدة الحالية. |

وجود الملف لا يعني تطبيقه في قاعدة ما. اقرأ `_prisma_migrations` قراءةً فقط وقارن الأسماء وchecksums بالملفات المعتمدة، وافحص سجلًا بلا `finished_at` أو مع `rolled_back_at`. لا تعِد كتابة Migration سبق تطبيقها. افحص DDL الفعلي والقيود والفهارس أيضًا؛ نجاح `migrate status` أو `migrate deploy` لا يثبت خلو المخطط من اختلاف يدوي. استخدم CLI المثبت مع المشروع، Prisma 6.19.3، ولا تسحب إصدارًا أحدث تلقائيًا.

لا تستخدم migrate dev أو db push أو reset أو Seed أو تعديلات SQL يدوية لحل اختلاف على المتجر. إذا غاب سجل أو اختلف checksum أو قيد، أوقف الانتقال وجهّز إصلاحًا منفصلًا على نسخة. `migrate resolve` يغيّر سجل الهجرة ولا يرجع SQL أو البيانات؛ ليس تراجعًا عاديًا.

الإنتاج يستخدم `LOGIN_RATE_LIMIT_STORE=postgres` ويغلق محاولة الدخول بأمان إذا غاب الجدول/المخزن. تشغيل الصورة الجديدة قبل هجرتها على **الهدف المعتمد** يعرض الدخول للفشل. لا تتجاوز ذلك بـmemory في الإنتاج. المخزن الذاكري مقصور على التطوير/الاختبار أو المعاينة المحلية الصريحة المقيدة بـloopback؛ لا يشارك الحد بين العمليات ولا عبر إعادة التشغيل.

## مراحل التجهيز اللاحقة

1. **اختيار هدف معزول:** حدد مضيفًا وسعة للقاعدة والوسائط وعدة نسخ وإصدارات مع هامش نمو، وإصدارات Docker/Compose، ونطاق HTTPS وTLS، ونسخًا مشفرة خارج المضيف. اختر مشروعًا وقاعدة وvolumes جديدة وشبكة خاصة غير متعارضة. لا تربط أيًا منها بالمصدر.
2. **تجربة الاستعادة:** بعد الموافقة عليها، خذ نسخة متسقة وفق BACKUP.md، واستعدها في قاعدة جديدة فارغة وvolume جديدة دون خيارات حذف. انقل الأسرار الأصلية سرًا وافحص البصمات والأعداد والحسابات والقيود قبل أي migration.
3. **تجربة الهجرة:** طبّق المفقود فقط على النسخة، وبصورة API المراجعة. وثق المدة والأقفال والنتيجة، ثم افحص بقاء أعداد بيانات العمل وعناوين الصور والحسابات كما هي. لا تستخدم صورة الاختبار على المصدر.
4. **قبول التطبيق:** اختبر القائمة التالية على النسخة وسجل النتائج الفعلية. اختبر المخزن المشترك عبر عمليات متعددة وإعادة تشغيل API وفشل المخزن الآمن. لا تفتح المتجر إذا فشلت الهجرة.
5. **تجربة التراجع:** احتفظ بالصور السابقة والنسخة السابقة وجرّب مسارًا من الجدول أدناه. أنشئ طلبًا بعد الانتقال **التجريبي** وأثبت أن التراجع لا يفقده.
6. **قرار القطع:** اجمع نتائج التحقق وخطة التوقف وRPO/RTO والمشغّل وتحويل المرور والعودة. اعتماد التحضير الحالي لا يجيز نشرًا أو هجرة أو تغيير بيانات لاحقًا؛ يأتي اعتماد التنفيذ بعد اكتمال الحزمة القابلة للمراجعة.

## قائمة قبول في النسخة المعزولة

- تعمل الصور بالمستخدم غير الجذر وتبقى قاعدة البيانات والصور والإثباتات بعد إعادة إنشاء الحاويات. لا تؤدي صلاحية كتابة خاطئة أو قرص ممتلئ إلى إعلان حفظ زائف.
- يطابق HTTPS أصل الموقع وأصول API؛ cookies محمية بـSecure/HttpOnly/SameSite وCSRF. لا يعمل استثناء HTTP للمعاينة العامة ولا توجد أسرار في bundle العميل أو build arguments أو سجل عام.
- يعمل حساب المسؤول الحالي بكلمة مروره دون reset أو بديل، وتُحترم أدوار MANAGER/SUPER_ADMIN. اختبر الحد المشترك وعنوان العميل عبر Caddy وعدم تجاوز الحد بـ`X-Forwarded-For` مزيف. `TRUST_PROXY` عنوان Caddy الثابت فقط؛ أي proxy إضافي يحتاج مراجعة مستقلة.
- تظهر الصور المحلية وصورها حسب اللون دون تغيير الروابط. الوصول العام إلى `/media/private/` و`/uploads/` والتخمين لا يعطي إثباتات؛ المسار المحمي يعطيها للمسؤول المخوّل فقط. يعمل رابط طلب قديم بالسر الأصلي دون نشر token.
- تطابق أعداد الطلبات والحسابات والمنتجات والإعدادات وإجمالي المخزون اللقطة وتعمل تقارير فترة معروفة. اختبر **في النسخة فقط** COD وInstaPay والإثبات ومراجعة الدفع والحالات والتحصيل والمرتجع الجزئي والمخزون وتزامن شراء آخر قطعة وتكرار نفس idempotency key.
- تعمل الصفحات والسلة والدفع والإدارة على الموبايل وRTL. افحص robots وsitemap والنطاق وSEO والشحن وInstaPay وWhatsApp والإعدادات التجارية الفعلية دون استبدالها ببيانات تجريبية.
- تنجح استعادة النسخة في هدف ثانٍ جديد وتُقاس مدتها. عند هدف غير فارغ أو اسم خاطئ يتوقف الإجراء قبل الاستعادة؛ لا يُحل الفشل بحذف هدف أو مصدر.

## نافذة انتقال بعد اعتماد مستقل

جهز الصور النهائية وملف الهدف الخاص وTLS ومراقبة الصحة قبل النافذة. إذا كان التحويل عبر DNS فاضبط TTL مبكرًا مع العلم أنه لا يزيل كل cache. اختر آلية تمنع الكتابة فعلًا، بما فيها API والإدارة، ومن يملك تحويل المرور؛ شاشة صيانة وحدها لا توقف API المتاح.

في النافذة: امنع الكتابة الجديدة وانتظر اكتمال الجاري، وأوقف عمليتَي التطبيق مع إبقاء PostgreSQL للنسخ. خذ **لقطة نهائية جديدة** للقاعدة والوسائط والأسرار المطابقة، ولا تستخدم نسخة التجربة القديمة. استعد في الهدف الجديد المتحقق منه وطبّق المفقود فقط، ثم افحص الصحة والأعداد والمخزون والصور والإثباتات.

يبقى المصدر متوقف الكتابة طوال التحويل وبعده لتجنب متجرين يستقبلان الطلبات. ابدأ تحقق قراءة ودخول محدودًا، ثم حوّل المرور وافتح الطلبات عند نجاح القبول. سجّل وقت آخر كتابة على المصدر وأول كتابة على الهدف؛ يحدد ذلك مسار التراجع. لا تنشئ أو تحذف طلبات تجريبية في قاعدة المتجر الحية كفحص نشر.

راقب الصحة وفشل الدخول وحفظ الطلب والصور و4xx/5xx والقرص والنسخ والتقارير دون تسجيل بيانات العملاء أو tokens. احتفظ بالمصدر والنسخة النهائية والصور السابقة خلال فترة القبول ولا تنظفها تلقائيًا.

## التراجع مع حفظ الطلبات اللاحقة

تراجع صورة التطبيق لا يرجع schema أو ملفات أو بيانات. لا تستعد dump قديمًا فوق قاعدة تستقبل طلبات ولا تشغّل migration عكسية عامة.

| الحالة | الإجراء |
| --- | --- |
| لم يستقبل الهدف أي كتابة | أوقف الهدف وأعد المرور إلى المصدر المحفوظ بعد إثبات أنه المرجع النهائي للبيانات. استخدم الصور والمخطط والوسائط المتطابقة؛ سجّل عدم وجود كتابات جديدة قبل القرار. |
| توجد كتابات على الهدف والتوافق مع الصور السابقة مثبت بالتجربة | أوقف الكتابة مؤقتًا وخذ نسخة حديثة من **الهدف الحالي** ووسائطه. شغّل api/web السابقين المعتمدين على **نفس قاعدة الهدف الحالية ونفس volume الوسائط** مع الأسرار الأصلية، دون migrate أو seed أو استعادة قديمة. افحص الدخول والحد المشترك قبل فتح الطلبات. |
| توجد كتابات على الهدف والتوافق غير مثبت | امنع الكتابة في الجانبين واحفظ نسخة كاملة حديثة من الهدف ووسائطه وتدقيقه. أبقِ الصيانة أو أصلح للأمام. أي رجوع لمخطط/بيانات أقدم يحتاج تصميمًا واختبارًا منفصلًا لتسوية **كل** الطلبات والمخزون والدفع والمرتجعات والمحاسبة والتعديلات منذ القطع؛ نسخ صفوف Order وحدها لا يكفي. لا تفتح المصدر القديم قبل إثبات التسوية. |
| فشلت الهجرة/الاستعادة قبل فتح الهدف | أبقِ المصدر محفوظًا وأوقف الهدف. لا تتجاوز الفشل بـmemory أو resolve أو حذف جدول. احفظ التشخيص المنقح وافحص السبب في هدف جديد معزول. |

إضافة عمود color القابل لـNULL وجدول حد الدخول توسعتان في المخطط، لكن هذا وحده لا يُثبت توافق الإصدار السابق: يجب تجربة الصور السابقة مع المخطط والبيانات والوسائط الجديدة. كما أن تسجيل دخول ناجحًا في الإصدار الجديد قد يرقّي hash قديمًا إلى صيغة `scrypt:v1`؛ إصدار أقدم لا يفهمها قد يفشل في دخول الحساب بعد التراجع. لا تعكس hash أو تعِد ضبط كلمة المرور لتجاوز ذلك؛ اعتمد صورة تراجع تقرأ الصيغتين واجتازت الاختبار أو أصلح للأمام.

الإصدار السابق الذي لا يملك الحد المشترك لا يُقبل تلقائيًا للتراجع العام؛ يجب أن يحقق حد الدخول المطلوب أو تبقى الصيانة حتى الإصلاح للأمام. لا تزيل جدول المحاولات لتشغيل إصدار أقدم، ولا تغيّر الأسرار القديمة.

احتفظ بـAPI_IMAGE/WEB_IMAGE السابقين في سجل خاص. بعد إثبات التوافق وتحديث المرجعين في ملف **الهدف** الخاص، إجراء الصورة فقط هو `dc up -d --no-build --no-deps api web`. لا تُشغّل migrate. لا تستخدم `up --build` كتراجع لأنه قد لا يعيد الإصدار الذي اختُبر.

## سجل الاعتماد قبل التنفيذ

| البند | القيمة/الدليل |
| --- | --- |
| المصدر والصور السابقة/الجديدة | لم يُعتمد نشر؛ يسجله مسؤول الإصدار. |
| النسخة النهائية والبصمات والأسرار المنفصلة | تحدد وقت القطع، وليست نسخة تجربة قديمة. |
| قاعدة/volumes ومشروع الهدف المعزول | تحدد وتراجع قبل أي أمر تغيير. |
| نتائج restore + migration + Docker/TLS | ترفق النتائج الفعلية؛ Docker غير منفذ ضمن التحضير. |
| أول كتابة على الهدف وخطة حفظ اللاحق | تسجل أثناء القطع وتحدد مسار التراجع. |
| توافق الصور والمخطط والوسائط وصيغ كلمات المرور | يلزم إثباته قبل قبول تراجع بالصورة فقط. |
| RPO/RTO والصيانة والاحتفاظ | يحددها مالك المتجر ومسؤول التشغيل. |
| المسؤول والموافقة على التنفيذ | لا تمنحها مهمة التحضير الحالية. |

المراجع: [pg_restore PostgreSQL 16](https://www.postgresql.org/docs/16/app-pgrestore.html)، [Compose profiles](https://docs.docker.com/compose/how-tos/profiles/)، وCLI Prisma المثبت في lockfile. لا تستخدم دليل إصدار رئيسي أحدث كتعليمات ترقية أثناء هذا الانتقال.
